A portfolio-safe reconstruction of a casino finance operation where handwritten physical documents were converted into structured, auditable data using AI Builder, Azure AI Foundry, Azure Functions, Power Automate, and Power BI.

What this shows: Finance operations depended on handwritten REM cards and related operational records. Important values were written on paper and needed to be captured into a consistent table before reports could be reconciled. The challenge was not only reading the document; it was preserving the relationship between card, account, balances, payments, vouchers, VAT, and gaming adjustments.

Implementation detail

How the solution works

Finance Operations / Document Intelligence / Reconciliation

The important part of this project is the complete operating chain: source capture, structured transformation, business-rule processing, exception handling, and reporting. Each stage produces a clear output that can be validated before the next stage uses it.

01 / DOCUMENT INTAKE

Physical REM cards and supporting documents were collected as the source of truth. Each image or scan was associated with a processing batch and a business date so the resulting record could be traced back to the original document.

Output: traceable, reviewable data for the next stage
02 / FIELD CAPTURE

The extraction process captured REM card number, account number, REM card balance, cash issued, chip payments, cash payments, and other transaction fields. Because handwriting and layouts can vary, captured values required validation and exception review.

Output: traceable, reviewable data for the next stage
03 / TABULAR STAGING

The document data was normalized into a structured table with consistent field names, data types, dates, amounts, and reference identifiers. This staging layer made the records usable in Excel, Power Query, Power Automate, SQL, or Dataverse-style storage.

Output: traceable, reviewable data for the next stage
04 / RECONCILIATION

Operational totals and financial movements were compared across source records and reports. The reconciliation logic covered vouchers in, vouchers out, VAT in, VAT out, free bets, match play logs, cash movements, chip movements, and balance differences.

Output: traceable, reviewable data for the next stage
05 / EXCEPTION REPORTING

Variances were isolated instead of being hidden inside totals. Exceptions could then be reviewed by finance operations with the original document reference, expected amount, captured amount, variance, and review status.

Output: traceable, reviewable data for the next stage

Example structured record

{ "source_reference": "BATCH-2026-001 / DOCUMENT-0042", "record_id": "REC-0042", "status": "review_required", "captured_fields": { "account_number": "sample-account", "document_number": "sample-document", "amount": 0, "tax": 0 }, "checks": { "required_fields": "passed", "duplicate": "not_found", "reconciliation": "variance_found" }, "next_action": "finance_review" }
Design principle: Never hide an exception inside a final total. Keep the source reference, extracted value, expected value, variance, and review status together so an operations user can explain what happened.
